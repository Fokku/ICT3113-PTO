## Title

Cascade design: small model first, the large model only when the rule says so

## Left: the diagram (Part 1)

`slides/drafts_a2/cascade_diagram.png`, generated by `cascade_diagram.py` from `service/cascade.py`. It shows:

- one ticket into `POST /tickets`;
- the small model (`granite4:3b`) with the unchanged classification prompt;
- the escalation rule (Setting A or B);
- **accept** returns the small model's category; **escalate** calls the large model (`qwen2.5:7b`) with the
  same unchanged prompt;
- the same response shape either way, so the caller cannot tell which model answered (brief, Step 2).

Both settings use the category rule, so there is no "long ticket skips the small model" path. The two settings' literal
conditions are printed under the diagram by `cascade_diagram.py`, from the code (`RULE_SETTINGS`), so the slide cannot show a
rule the service does not run. Regenerate with
`python slides/drafts_a2/cascade_diagram.py --small granite4:3b --large qwen2.5:7b`.

## Right, top: the rule in full (Part 2, from `cascade/escalation_rule.md` §2)

- **Method:** category-based (the brief's example method 1): accept the small model only on the categories it is reliable on.
- **Signal:** `granite4:3b`'s predicted category for the ticket, from its reply to the unchanged prompt, normalised to one of
  the seven canonical names or `UNPARSEABLE`. Nothing else is read.
- **Condition:** `escalate = predicted_category NOT IN ACCEPT[setting]` (exact match on the canonical name).
  `UNPARSEABLE` is never accepted, so it always escalates. If escalated, `qwen2.5:7b` is called once, with the same
  prompt, and its answer is final. A failed small-model call is an error, not an escalation.
- **The rule never reads the true label.** It sees only what the small model produced for this ticket.

## Right, middle: the two settings tested (Part 2, from §3)

| | Setting A | Setting B |
|---|---|---|
| Accept-set (`ACCEPT`) | {Mortgage, Consumer loan, Debt collection} | {Mortgage, Consumer loan, Debt collection, **Credit card**} |
| How chosen | categories granite got right every time on the tuning set (12/12, 5/5, 4/4) | the lowest escalation that still passes both limits on the tuning set (≥ 5 predictions per accepted category) |
| Escalation on the tuning set (count) | 78/99 (78.8%) | 59/99 (59.6%) |
| Wrong granite answers let through, tuning set | 0 of 30 | 8 of 30 (all "Credit card") |

Both settings were chosen on the 99 tuning rows only. The 101 test rows were not used.

## Right, bottom: why this rule (Part 2, one or two lines from §2)

Category-based adds no model call: every ticket pays one `granite4:3b` call and only escalated tickets pay a second.
**Agreement** (granite vs `llama3.2:3b`) escalated the same 59/99 as Setting B for a two-ticket accuracy gain (76 vs
74/99, within noise) while adding a second small-model call to every ticket and a third resident model.
**Ticket length** does not predict granite's errors (median 774 characters when wrong vs 720 when right).
**Self-reported confidence** would need a prompt change (forbidden) or an extra call on every ticket.
